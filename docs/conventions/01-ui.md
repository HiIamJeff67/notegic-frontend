# UI Conventions

## Foundation

- Use Tailwind CSS v4 utilities for layout, spacing, responsive behaviour and component-local appearance.
- Use the shadcn-style primitives in `apps/web/src/components/ui/` for controls and overlays. They own Radix/Base UI accessibility behaviour and `data-slot` attributes.
- Compose application patterns in `apps/web/src/components/commons/`, `core/`, `menus/` and `panels/`; do not recreate Button, Dialog, Sheet, Menu, Input or Tooltip from raw HTML.
- Use Radix/Base UI directly only when adding a missing primitive to `apps/web/src/components/ui/`. Feature code should consume the local wrapper.
- Use `lucide-react` for general UI and action icons. Use custom icons only for Notegic-specific concepts.

## Composition and interaction

- Prefer an existing UI primitive, then an existing common component, before introducing a new component.
- When the same action is available from several entry points, route them through one owning dialog or component. Entry points may pass different context and completion callbacks, but must not duplicate or fork the interaction UI.
- Keep each interactive control accessible: icon-only controls need an `aria-label` or a visible tooltip; destructive actions need the destructive variant/state.
- Use `ContextMenuItem`, `DropdownMenuItem` and related wrappers for menu rows so keyboard behaviour and density remain consistent.
- Use `Button` rather than a raw `button` unless a primitive explicitly needs a raw trigger. `Button` publishes `data-slot="button"` and `data-size` for shared styling.
- Use the entity icons exported from `apps/web/src/components/icons/WorkspaceEntityIcons.ts` whenever rendering a workspace entity.

## Reuse the owning interaction

Before adding a UI, search existing feature entry points, common components,
primitives and their tests for the same user need. Reuse the component that owns
the interaction, not just its icons or classes. An existing dialog, picker,
viewer, menu, notification or loading flow must not be copied into a second
implementation merely because it opens from another feature.

Pass the caller's context, state or completion callback to the established
owner. Extend it only when the existing contract cannot express a real current
need; do not add a generic wrapper or flags for hypothetical reuse. Keep theme,
density, accessibility, keyboard handling, errors and tests on that same path.
If reuse is unsuitable, record the concrete behavioral or ownership difference
before introducing a separate implementation. See
[Reuse before creating](05-helpers-and-abstractions.md#reuse-before-creating)
for the corresponding helper, hook and data-boundary rules.

## Loading feedback

For every new loading UI, first evaluate the existing blocking-cover flow in
`components/covers/LoadingCover/` and `LoadingProvider`. Historical references
to `StrictLoadingCover` refer to this flow; do not create another named cover
or a feature-specific spinner, overlay or loading banner to replace it.

- Use the shared cover when work makes the current screen unsafe or unusable,
  such as navigation, opening a large document, parsing or its first render.
  Heavy work is a reason to evaluate blocking, not to block every background API.
- Router pending state and explicit strict transactions are owned by
  `LoadingProvider`, which renders `AppLoadingCover`. For an event-owned promise,
  use `useLoading().startAsyncTransactionLoading(operation, "strict")` rather
  than manually starting and stopping a second counter.
- For component/query-owned readiness, keep the state with its owner and render
  `<LoadingCover condition={isLoading} />` alongside the mounted content. It
  suppresses its own cover while the provider's strict cover is active. Combine
  prerequisite states at the nearest common owner; do not stack one cover per
  request, parser or child renderer. Use the existing
  `useRegisterLoadingDependencies(isLoading)` to report that state to the lax
  indicator and unregister it on unmount, as the authentication and Material
  screens do.
- Cover the actual prerequisite chain: a signed URL is not a ready preview.
  Release the cover on completion, failure, cancellation or unmount, and ensure
  stale completions cannot end another operation's loading state. Preserve
  editor/viewer state rather than changing keys or replacing the owner to reload.
- Do not block normal typing, drawing, zoom/page repaints, background refresh
  that leaves the screen usable, or continuous audio/video buffering. Where
  feedback is needed, reuse existing control/native media pending behavior.
- `isLaxLoading` includes provider strict work and registered dependencies, but
  does not itself display a cover. `useRegisterLoadingDependencies` reports lax
  dependencies; it does not make them strict. A conditional `LoadingCover`
  displays blocking UI but does not change the provider's strict indicator.

Validate success, error, retry, unmount, stale results and overlap with router
or transaction loading using the real shared cover/provider. Assert that one
cover is shown, it disappears when appropriate, and user edits are retained;
do not replace the cover with a feature-specific fake in those tests.

## Toast feedback

Use the existing `toast` facade from `@shared/lib/toast/toast` for application feedback.
`components/ui/toast.tsx` adapts the official shadcn Base UI Toast primitives and
creates the official manager; `components/ui/toaster.tsx` owns the single provider
around the application in `RootDocument`. Base UI owns the notification list,
timeouts, hover/focus pausing, swipe dismissal and keyboard access. Do not add a
second store, queue, timer or custom subscription hook. `useToastManager` is
available from the local primitive only for components inside that provider.

Translate messages at the presentation boundary with the project's
`@shared/i18n/useTranslation` and existing `tError` for errors. The toast facade
does not translate or capture a language. Retained async callbacks should use
the project's current-language translation function.

```tsx
const { t } = useTranslation();
toast.success(t("workspace.notifications.widgetsSaved"));
toast.error(tError(error, t));
```

Success defaults to 2 seconds, information to 3 seconds, and warnings, errors
and plain notifications to 5 seconds. `duration` overrides milliseconds;
`0` or `Infinity` keeps a toast until dismissal. `toast.dismiss(id)` or the
returned `{ id, dismiss }` handle closes it; `toast.dismiss()` closes all.
Empty success/error messages remain suppressed.

Desktop and mobile default to `top-center`; ordinary callers, including
dashboard widgets-saved notifications, should not repeat the default position.
Desktop callers can override `position` with any of `top-left`, `top-center`,
`top-right`, `bottom-left`, `bottom-center` or `bottom-right`. All mobile
notifications share the top-center stack, including desktop overrides.
Placement and stack direction use responsive CSS around the same Base UI
provider; do not create a provider/store per location.

## Local UI logic

- Keep one-use event handlers, display mapping, conditional rendering, and
  component-local derived values in the component when they remain readable.
- Do not create a helper function file for logic used by only one component.
  A short local function may remain in the component file when naming improves
  readability.
- Do not extract a component helper merely because it contains more than one
  statement. Extract only when the logic is reused, has a clear UI/domain
  concept, or hides the primary interaction flow.
- Do not create a generic `helpers.ts`, `common.ts`, or `utils.ts` module for
  unrelated UI fragments. Keep ownership beside the component or feature.
- Keep component-local types and constants in the component file when they are
  not used elsewhere. Promote them only when a second real consumer exists.

## Documentation code examples

Use `components/panels/CodeExamplePanel/CodeExamplePanel.tsx` for documentation
snippets. It composes the
official [shadcn Code Block](https://ui.shadcn.com/docs/components/radix/code-block)
primitives in `components/ui/code-block.tsx` with the existing Radix-based
`TabsList`, `TabsTrigger` and `TabsContent`; do not use ToggleGroup for code tabs
or create another copy/highlight implementation.

```tsx
<CodeExamplePanel title="Example" code={{ curl: curlExample, http: httpExample }} />
<CodeExamplePanel title="Response body" code={{ json: JSON.stringify(body, null, 2) }} />
```

Other features can compose `CodeBlockHeader`, `CodeBlockTitle`,
`CodeBlockActions`, `CodeBlockCopyButton`, `CodeBlockContent` and `CodeBlockLine`
directly. The copy button takes the original string through `value`, independently
of the scrollable content. For highlighting, use `useHighlightedCode` from
`@/hooks/useHighlightedCode`; React lifecycle and the streaming-line cache stay
in this hook. Language configuration, the shared Shiki instance, lazy loading
and tokenization live in `shared/lib/code/codeHighlighter.ts`, also used by BlockNote. Shiki's
core, JavaScript engine, themes and supported grammars load only when requested.
The hook returns plain-text lines before loading and token lines after loading;
it does not return JSX. `CodeExamplePanel` imports its sibling `CodeExample.tsx`,
which renders those lines with the official `CodeBlockLine` and token spans.
Do not add a Provider, a separate `lib/` rendering module, or compatibility
re-exports merely to split TypeScript from JSX.
SSR and a failed optional highlighter load retain escaped, readable text.
Tokens switch light/dark palettes through CSS, not a second theme subscription.

Editable code belongs to BlockNote, not the documentation `CodeExample` renderer.
BlockNote's complete React schema is constructed without parameters by
`createBlockPackSchema()` in `shared/lib/blockpack/editor.ts`.
The same module creates the shared `notegicBlockPackSchema` instance after the
editor class is initialized, exported through the package's `index.ts`; Web editors use that
instance. Custom block specifications live in `specs/`. The Calendar spec uses
`react-day-picker` directly with its official CSS module and semantic theme
tokens, without injecting a Web component or importing Web UI into shared.
Project-owned menus (`SuggestionMenu.tsx`, `BlockSideMenu.tsx` and
`PatternToggleButton.tsx`) live with the Web `BlockPackEditor`. Preserve
external BlockNote API names while using SuggestionMenu for project-owned
slash command composition.

`shared/lib/blockpack/editor.ts` registers the official `SyntaxHighlightingExtension`
for both collaborative BlockPack and local Payload editors. Their shared
`codeBlockSpec` retains the official code renderer, language picker, keyboard
handling and serialization. Unknown/legacy language properties must remain
readable and unchanged; add their current value to the rendered picker rather
than rewriting the document. Supported aliases resolve only for highlighting.
Keep editor theme/picker overrides in `block-editor.css`; do not rebuild an
editor or replace its content when loading a grammar or switching languages.
Both `BlockNoteView` surfaces pass the current `useTheme().currentTheme.isDark`
as the explicit `theme` prop. Do not fall back to the system preference: the
vendor's nested light/dark class also defines application semantic tokens.

## Responsive layout

- Page content must have `min-w-0` in flex layouts and must wrap or stack instead of overflowing.
- App-only pages live below `_root`; public pages must be root routes and cannot rely on the app sidebar or account providers.
- Sheet, dialog and sidebar content must keep close/primary controls reachable at narrow widths.
