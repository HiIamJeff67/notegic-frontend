# 2026-08-26 — Frontend Monorepo Phase 1

## Context

The repository currently contains one Web application and a transitional
`shared/` tree. `shared/api/` mixes portable API/query code with Web runtime
adapters, while i18n, reducers, assets, and styles still live under the Web
source tree. The architecture must support future Web, Desktop, and Mobile
applications without assuming one specific Desktop or Mobile framework.

## Decision or change

- `shared/` owns reusable TypeScript code and packages with real multi-app consumers, public/generated contracts, or cross-platform invariants.
- HTTP request/response is the lowest common API boundary.
- Web and Desktop may optionally use TanStack Start `serverFn`; Mobile may use direct HTTP. No server function is a database connection or cross-runtime write path.
- GraphQL and generated contract artifacts are shared consumer inputs/output; backend public contracts remain authoritative and generated files are never hand-edited.
- Shared i18n owns resources, language types, and pure helpers. `shared/i18n/language.ts` owns language definitions/checks; each app owns stored-language synchronization and storage/lifecycle integration.
- Portable reducers may move to shared; editor-specific reducer dependencies require an explicit boundary.
- Assets are copied and owned per app. There is no initial `shared/assets`.
- Web CSS, Tailwind, BlockNote/editor styles, browser metadata, and Web packaging remain Web-owned. Platform-neutral design tokens may be shared.
- The current TanStack Start server-capable Web deployment targets Cloudflare Workers/Workers Builds first. Pages is a static-output option only when SSR/server functions are not required.
- Daily devlog snapshots are generated by `scripts/devlog.mjs`, exposed through `npm run devlog` and `node scripts/devlog.mjs`, and summarized from local Git history. `npm run devlog:fetch` refreshes GitHub remote refs and `npm run devlog:backfill` recreates historical snapshots from `origin/main`. The generator also refreshes the marked Development log section in the root README; it does not call an AI service.

## Consequences

Phase 2 can create `apps/web`, `apps/desktop`, `apps/mobile`, and more explicit
shared workspace boundaries without changing the ownership decisions. Until
then, current paths remain valid and new portable code should avoid Web-only
dependencies. Cloudflare build configuration must include the relevant app,
shared code, root manifests, lockfile, and codegen inputs from the same GitHub
repository.
