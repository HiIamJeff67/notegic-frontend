# Documentation and Linear naming

Use this skill when creating or revising repository documentation, Linear project planning content, milestones, issue titles, or Codex skills in the Notegic frontend repository.

## Source of truth

Before writing, read the relevant local documentation:

- Start with [docs/README.md](../../docs/README.md) and [docs/conventions/README.md](../../docs/conventions/README.md).
- Use the document index to select the narrowest applicable convention; do not load unrelated documents.
- Treat the current codebase and current Linear state as the source of truth when older notes conflict.
- Record cross-cutting decisions in the appropriate `docs/conventions/` or `docs/designs/` document instead of duplicating them in a chat or issue.

## Documentation placement and writing

Choose the document type by the question it answers:

- `docs/designs/`: current route, codebase, system, and contract decisions.
- `docs/conventions/`: contributor rules and durable repository conventions.
- `docs/runbooks/`: repeatable development, verification, or troubleshooting procedures.
- `docs/devlogs/`: dated implementation history generated by the repository workflow.

Keep documents scoped, concise, and actionable. Prefer:

1. Goal and non-goals.
2. Ownership and boundaries.
3. Procedure or decision.
4. Validation and acceptance criteria.
5. Dependencies, rollback, or known limitations when they materially affect the work.

Write all repository documentation under `docs/` in English. Use English for
titles, prose, code comments in documentation examples, and operational
instructions so the two repositories remain searchable and consistent.

Use checkboxes only for independently verifiable work. Do not mark an item complete without evidence. Do not turn a historical devlog into the canonical design source.

For frontend repository changes, follow [docs/conventions/07-version-control.md](../../docs/conventions/07-version-control.md): commit messages use lowercase English descriptions, and `npm run devlog` output is committed with the functional change rather than in a devlog-only commit. Also respect [docs/conventions/04-file-and-folder-naming.md](../../docs/conventions/04-file-and-folder-naming.md) for file and folder names.

## Linear naming and structure

Apply these rules to Linear content:

- Every milestone name uses exactly `Milestone <number> - <description>` with an ASCII hyphen.
- Number milestones sequentially within each project, starting from the project's established first number. Preserve existing order and do not renumber unrelated milestones without an explicit migration request.
- Do not prefix a milestone name with `Phase <number>`, `Project`, `TODO`, status text, or a repository name. Historical phase terminology may remain inside a description when it documents the decision, but the milestone name must use `Milestone`.
- Issue titles must not begin with `Phase <number>` (including `Phase 0`, `Phase 1:`, or `Phase 5 —`). Put the phase or milestone association in Linear metadata instead.
- Issue titles should state a concrete domain outcome or action. Avoid repository-wide labels such as `backend` or `frontend` unless they distinguish a real ownership boundary; use Linear project, team, labels, and milestone fields for that metadata.
- Keep titles short enough to scan, avoid sentence-like implementation detail, and do not put status or checklist text in the title.
- An issue description should make scope, non-goals, dependencies, checklist, and acceptance evidence clear. Create a new issue only when an existing issue cannot own the work; avoid splitting one outcome into many administrative issues.

When cleaning existing content, rename only the scoped titles and milestones required by the request, preserve IDs, status, order, relations, descriptions, and completed history unless the request explicitly changes them.

## Skill format

A skill is a lower-kebab-case directory containing a required `SKILL.md`. Its frontmatter must include lowercase `name` and a concise `description`. The body should contain only the trigger, scope, decision rules, workflow, and references that change agent behavior.

Optional `agents/openai.yaml` is for UI metadata; `references/` is for substantial, conditionally loaded material. Do not add a README, placeholder scaffold, or duplicate manual unless it supports a real workflow. Keep references linked from `SKILL.md`, and read only the references needed for the current task.

Validate a new or substantially revised skill with `quick_validate.py` from the skill-creator package. Preserve implicit invocation unless the user explicitly requests an explicit-only skill. Keep frontend and backend copies aligned in shared rules while pointing each copy to its own repository documentation.

## Safe update workflow

1. Inspect the current document, Linear project, milestone, or issue before editing.
2. Apply the smallest scoped change and preserve existing IDs and relationships.
3. Re-read the result and check naming, links, checklist evidence, and document placement.
4. For repository changes, run the relevant local verification before delivery.
